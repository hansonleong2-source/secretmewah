# secretmewah — real database edition

This version keeps the GitHub Pages frontend but moves authentication, posts, likes, comments, follows, notifications, messages and image uploads to Supabase.

## 1. Create the Supabase backend

Create a Supabase project, then open **SQL Editor**.

Paste and run the complete `supabase.sql` file.

It creates:
- `profiles`
- `posts`
- `post_likes`
- `comments`
- `follows`
- `notifications`
- `messages`
- `post-media` Storage bucket
- Row Level Security policies
- notification triggers
- Realtime publication entries

## 2. Put your Supabase keys in config.js

Open `config.js` and replace:

`PASTE_YOUR_SUPABASE_PROJECT_URL_HERE`

and

`PASTE_YOUR_SUPABASE_PUBLISHABLE_KEY_HERE`

with the project's URL and publishable key from the Supabase API settings.

Use only the browser-safe publishable/anon key. NEVER put a `service_role` or secret key in GitHub Pages.

## 3. Authentication

The website supports:
- Email/password sign up
- Email/password login
- Supabase session persistence
- Logout
- Profile creation through a database trigger

If email confirmation is enabled in your Supabase Auth settings, users will need to confirm their email before logging in.

## 4. GitHub Pages

Upload all files in this folder to your repository:

- index.html
- style.css
- app.js
- config.js
- supabase.sql
- assets/logo.jpeg

Then GitHub:
Settings → Pages → Deploy from branch → main → / (root).

## 5. What is now real

Unlike the previous localStorage demo:
- accounts are stored in Supabase Auth
- profiles are stored in Postgres
- posts are shared across devices
- images upload to Supabase Storage
- likes/comments/follows are stored in the database
- notifications are generated by database triggers
- messages are stored in the database
- selected updates use Supabase Realtime

## Security

RLS is enabled on the application tables. The browser uses the public/publishable key only. Do not expose a Supabase secret/service-role key in frontend files.
